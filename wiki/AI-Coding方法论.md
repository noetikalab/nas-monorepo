# 我的 AI Coding 方法论

> 基于 Claude Code + 多实例协作 + 结构化文档体系的个人工程实践总结。

---

## 核心理念

**AI 是执行引擎，人是决策者。**

AI 写代码的速度远超人类，但它不关心架构是否合理、接口是否一致、文档是否过时。我的角色不是"提示词工程师"，而是**架构决策者 + 质量把关人 + 知识管理者**。AI 负责广度（写代码、查资料、做实验），我负责深度（判断方向、纠正偏差、沉淀知识）。

三条铁律：

1. **AI 先提案，人再纠偏。** 永远不让 AI 在未经确认的情况下做方向性决策。
2. **先理解原理，再动手。** 不懂原理只记命令，出任何偏差都束手无策。
3. **完成即沉淀。** 每次工作结束，有价值的信息必须写入文档，不让知识蒸发。

## 一、基础设施：CLAUDE.md 分层体系

### 设计原则

CLAUDE.md 是项目的"AI 可读手册"。核心原则：**写"为什么"不写"是什么"。** 代码和目录结构本身说明"是什么"，文档的价值在于解释背后的原因、约束和决策。

### 三层结构

```
根 CLAUDE.md          → 项目全局：技术栈、核心决策、注意事项、外部文档索引
  │
  ├── 子模块/CLAUDE.md   → 模块专项：目录结构、API 路由、踩坑记录、约束
  │
  └── main-claude.md    → 跨实例同步：当前阶段、已完成工作、API 参考、分工
```

### 每层的内容模板

每个 CLAUDE.md 包含以下固定章节：

| 章节 | 内容 | 受众 |
|------|------|------|
| **项目概述** | 一句话 + 技术栈 | 新 AI 实例 |
| **关键决策** | 为什么选 A 不选 B | 所有实例，避免推翻已有决策 |
| **目录/架构** | 文件在哪、职责是什么 | 需要改代码的实例 |
| **常用命令** | 复制即用 | 需要运行/测试的实例 |
| **API/路由** | 接口清单 | 跨模块开发（前端调后端、APP 调后端） |
| **踩坑记录** | 现象→根因→修复 | 所有实例，避免重复踩坑 |
| **约束** | 版本锁、命名规范、禁用手法 | 所有实例，防止破坏性变更 |

### 信息密度检查

写进 CLAUDE.md 之前问自己：
- 这个信息能不能从代码里直接读出来？能 → 不写
- 这个信息是不是"别人看了就知道为什么这样做"？是 → 写
- 这个信息的保质期是多久？临时调试 → 不写；长期约束 → 写

## 二、文档策略：四种文档各司其职

```
飞书文档  = 给别人看的（正式、完整、美观、可分享）
CLAUDE.md = 给 AI 看的（精简、结构化、高密度、仅本地）
main-claude.md = AI 实例间通信的（状态同步、进度跟踪）
本地 .md  = 给自己反复查阅的（技术总结、学习笔记）
```

| 类型 | 载体 | 受众 | 更新频率 | 触发条件 |
|------|------|------|---------|---------|
| **设计文档** | 飞书 | 人类（导师、同事） | 低频 | 重大架构变更 |
| **同步文档** | main-claude.md | AI 实例间 | 高频 | 每次工作后 |
| **操作手册** | CLAUDE.md | AI 实例 | 中频 | `/project-sync-docs` |
| **知识资产** | 飞书专栏 | 自己（学习/面试） | 按需 | 深入学习新领域后 |

### 关键规则

1. **CLAUDE.md 绝不在 AI 不知道的情况下过时。** 每次完成工作后用 `/project-sync-docs` 即时同步。
2. **main-claude.md 是"多 Agent 共享状态"**，格式固定、章节固定，任何实例都能 10 秒理解当前进度。
3. **飞书文档是"知识产品"**，需要排版、代码高亮、结构化表达，不能直接 dump markdown。

## 三、Skill 体系：把重复协作模式编码为规则

### 分层策略

```
用户级 Skills（~/.claude/skills/）
  → 跨项目通用：飞书操作、文档处理、代码审查、前端设计
  → 和项目无关，任何项目都能用

项目级 Skills（项目/.claude/skills/）
  → 项目特定：commit 规范、PR 流程、Android 开发闭环
  → 这个项目的团队规范
```

### Skill 设计四要素

| 要素 | 说明 | 例子 |
|------|------|------|
| **触发条件** | 什么场景触发 | "修改原生代码"、"说 commit" |
| **步骤流程** | 具体怎么做 | `git status` → `git diff` → 分析 → `git add` → commit |
| **失败处理** | 出错了怎么办 | 编译失败：提取错误→分析根因→告知用户→等确认→再修 |
| **禁忌规则** | 绝对不能做什么 | 禁止 `git add -A`、禁止 `--no-verify` |

### 最核心的三个 Skill

| Skill | 解决的问题 |
|-------|-----------|
| **project-commit** | 提交规范化——不用每次手写 Conventional Commits |
| **project-sync-docs** | 文档保鲜——完成工作后即时提取价值写入文档 |
| **android-dev-cycle** | Android 构建闭环——编译→安装→日志，含完整的失败处理协议 |

### 何时写一个新 Skill

当同一个协作模式重复 3 次以上时，把它写成 Skill。判断标准：
- "每次做 X 我都要跟 AI 解释怎么做" → 写 Skill
- "这个项目有特殊的代码规范 AI 总会违反" → 写 Skill
- "这个操作出错后 AI 的处理方式总不对" → 写 Skill（重点写失败处理）

## 四、协作模式：怎么和 AI 配合最有效

### 模式 1：方案先行，杜绝盲写

```
❌ 你："帮我写文件管理功能"
   AI：直接写 500 行代码
   你：发现方向全错，白干

✅ 你："开发文件管理模块"
   AI：分析现状 → 提出方案（含路由设计、鉴权逻辑、数据结构）
   你：审视方案 → "接口和页面路径要区分"
   AI：调整方案 → 确认后开始执行
```

**关键**：AI 的第一个回答应该是方案，不是代码。让 AI 先说清楚"打算怎么做、为什么这样做"。

### 模式 2：分层验证，逐层排查

遇到问题时，永远从最底层开始验证，逐层向上缩小范围：

```
排查"文件上传挂起"：
  ① curl 直连 Go 后端  → 正常 ✓  → 排除后端
  ② curl 经 nginx       → 正常 ✓  → 排除 nginx
  ③ 浏览器经 nginx      → 挂起 ✗  → 问题在浏览器→nginx 链路

结论：Docker 构建缓存导致前端 bundle 过时
```

**原则**：每层一个变量，不要同时改两个东西。这是科学方法，不是 AI 技巧。

### 模式 3：已知问题不阻塞进度

```
遇到暂时解决不了的问题：
  ① 记录到 CLAUDE.md：现象 + 排查过程 + 当前结论
  ② 标注优先级：P0（阻塞）/ P1（绕过的方案）/ P2（不影响）
  ③ 继续推进其他工作
```

**原则**：未解决的问题不是"未知的 Bug"，是"已知但待解决的事项"。记录在案意味着下一个 AI 实例不用重新排查。

### 模式 4：纠正 AI 时要说明"为什么"

```
一般用户的纠正：  "不对，改 XX"
我习惯的纠正：    "不对不对，前面接口名字和页面路径看起来一样，
                  这会混淆 nginx 路由，把所有后端接口加 /api/ 前缀"
```

**为什么这很重要**：如果你只说"不对，改成 XX"，AI 只知道结果但不知道原因。下次遇到类似场景，AI 可能再犯同样的判断错误。说明原因 → AI 把原因内化到后续决策中。

## 五、多实例协作

### 架构

```
实例 A（主实例 - 后端/架构）
  ├── ldap-demo（Go authd + PUF 集成）
  ├── 维护 main-claude.md  ← 中枢同步文档
  └── 架构决策、接口设计

实例 B（APP 实例）
  ├── NasApp（React Native）
  ├── NFC / WiFi P2P
  └── 读取 main-claude.md 获取 API 参考

实例 C（前端实例）
  ├── nas-web（Next.js 管理后台）
  └── 文件管理 / Dashboard
```

### 共享状态协议：main-claude.md

| 章节 | 作用 | 更新者 |
|------|------|--------|
| 当前阶段 | 10 秒理解项目到哪了 | 主实例 |
| 已完成工作 | 告诉所有实例"别重复做" | 主实例 |
| 架构决策记录 | 告诉所有实例"已经定了，别推翻" | 主实例 |
| API 参考 | 让其他实例不用跨代码库查找 | 主实例 |
| 待实现 | 所有实例都能看到下一步做什么 | 主实例 |
| 分工说明 | 明确边界，避免两个实例做同一件事 | 主实例 |

**为什么不用 MCP Server / 消息总线？**

朴素方案有时候就是最优方案。一份结构化 Markdown 文件不需要任何基础设施，人类可读，AI 可解析，git 可追踪变更历史。多 Agent 通信的难度往往不是因为"消息传不过去"，而是"状态说不清楚"。main-claude.md 恰好解决了后者。

### 实例间不互相修改对方的 CLAUDE.md

每个实例只维护自己子模块的 CLAUDE.md。主实例负责更新 main-claude.md 的共享部分。这个边界清晰，不会出现两个实例同时改同一个文件导致冲突。

## 六、知识沉淀：从对话到资产的转化

### 三级沉淀

```
对话内容
  │
  ├── 即时价值（调试、临时修改）→ 不沉淀，对话结束即消失
  │
  ├── 项目价值（架构决策、踩坑、约束）
  │     → /project-sync-docs → AGENTS.md / main-claude.md
  │
  └── 长期价值（领域知识、技术原理、方法论）
        → 手动整理 → 飞书专栏 / 本地 .md
```

### 飞书的实际定位：发布层

飞书在我的体系里不是"第二大脑"——它是一个**发布层**。知识真正的生产、组织、检索、迭代全部在本地发生。飞书的作用：
1. **给同事/导师看**（办公系统分享链接）
2. **排版美化**（代码高亮、callout、表格等飞书渲染得比 markdown 好）

### LLM Wiki 模式：知识管理的协作协议

参考 [Karpathy 的 LLM Wiki](https://github.com/Astro-Han/karpathy-llm-wiki) 理念：**"AI 负责维护知识库，人类负责阅读和提问。"** 把知识管理建模为人类和 AI 之间的协作协议。

#### 知识文档的组织方式

```
raw/              ← 不可变源材料层
  ├── topic-a/     ← 原文存档，AI 只读不写
  └── topic-b/

wiki/             ← 编译后的知识层
  ├── topic-a/     ← AI 合成后的知识页
  ├── index.md     ← 全局目录（Agent 检索入口）
  └── log.md       ← 追加式操作日志
```

**组织原则：**
- **源材料不可变**：raw/ 里的东西 AI 只读不写，原始信息永远可追溯
- **知识页是合成产物**：不是原文摘要，而是跨多个源材料重新组织
- **一级分类 + 交叉引用**：一层子目录，知识关联靠 See Also 表达
- **全局索引为唯一入口**：index.md 表格，一行一篇文章 + 摘要 + 更新日期，Agent 不需要打开所有文章就能定位

#### 知识文档的更新迭代模式

| 模式 | 说明 |
|------|------|
| **Ingest（摄取）** | 新源材料 → 存入 raw/ → AI 编译进 wiki/。与已有文章同主题则合并，新概念则新建，跨主题则交叉引用 |
| **Cascade Update（级联更新）** | 一篇文章变更后 → 扫描同目录 + 全局索引 → 每个受影响的文章都更新 |
| **Conflict Resolution（冲突处理）** | 新旧内容矛盾 → 标注分歧 + 源归属，不做"哪个对"的判断 |
| **Archive（归档）** | 查询结果存档为独立页面，标记 [Archived]，永不参与级联更新 |

#### Agent 检索知识的方式

```
RAG 模式（查询时检索）:
  用户问 → embedding → 向量检索 → rerank → 生成
  缺点: 每次重复做阅读理解，跨文档关系靠 embedding 猜

LLM Wiki 模式（摄取时合成）:
  用户问 → 读 index.md → 精确打开 2 篇文章 → 生成
  优点: 知识在摄入时已结构化，关系显式表达
```

**三种检索路径：**
1. **目录浏览**：index.md 按主题找 → 读文章。适合不知道关键词
2. **摘要匹配**：index.md 的 Summary 列本身就是检索目标
3. **交叉引用**：文章 A 的 See Also → 跳 B → B 的 See Also → 跳 C

#### 我的体系 vs LLM Wiki

| 维度 | LLM Wiki | 我的当前体系 |
|------|----------|-------------|
| 源材料 | raw/ 不可变 | 无独立 raw/，混在对话里 |
| 知识页 | wiki/ AI 合成 | AGENTS.md + main-claude.md + 飞书 |
| 索引 | index.md 表格 | 无全局索引，靠文件名定位 |
| 检索方式 | 读 index → 定位 → 读文章 | 直接打开 AGENTS.md / 搜索飞书 |
| 更新触发 | 每次 ingest 级联更新 | /project-sync-docs 手动触发 |

**最大差距**：缺少统一的 index.md（全局目录），知识页和源材料混在一起，知识更新没有级联机制，交叉引用靠人脑记忆。

## 七、踩坑管理方法论

### 踩坑记录的三要素格式

```
### [坑的标题]

**现象**：[实际看到什么]
**根因**：[为什么会这样]
**修复**：[具体做了什么]

⚠️ 如果是暂未解决的，额外标注：
**暂未解决** — [当前排查进度和已知结论]
```

### 为什么踩坑记录是 CLAUDE.md 最有价值的部分

1. **节省时间**：别人（或未来的你）遇到同样问题，不用从零排查
2. **节省 token**：AI 读到踩坑记录就知道"这个方向不通"，不会重复尝试
3. **建立信任**：当 AI 建议一个方案时，你可以检查 CLAUDE.md 里有没有"这个方案之前试过，不行的"记录

## 八、完整工作流：一次典型协作的全过程

```
① 你提出需求
   "开发文件管理模块"

② AI 分析现状 + 提出方案（Plan Mode）
   分析已有代码 → 设计路由/鉴权/数据结构 → 列举变更文件清单
   → 你审视方案 → 提出修正 → AI 调整 → 确认

③ AI 执行开发
   按方案逐步实现 → 遇到问题 → 分层排查 → 修复
   → 构建验证 → 运行验证

④ 你发现问题 → AI 分析根因
   "列表模式什么都不显示"
   → AI：测量发现 Virtuoso height=0
   → 根因：父容器 flex-1 无 display:flex
   → 修复：ResizeObserver 动态测量

⑤ 完成 → 同步文档（/project-sync-docs）
   → 新增接口写入 main-claude.md APP API 参考
   → 踩坑记录写入 nas-web/CLAUDE.md
   → 架构决策写入 ldap-demo/CLAUDE.md

⑥ 提交代码（/project-commit）
   → 分析变更 → 精选暂存文件 → Conventional Commits → 确认提交

⑦ 知识沉淀（可选）
   → 这个话题有学习价值 → 写飞书专栏
```

## 十条准则

1. **AI 提案，人做决策。** AI 提供方案，你来判断对错。
2. **方案先行，代码在后。** AI 的第一个输出应该是方案，不是代码。
3. **分层验证，逐层排查。** 一个问题一个变量，不瞎猜。
4. **已知问题记录在案，不阻塞进度。** 记下来让别人不用重新排查。
5. **纠正 AI 时说明"为什么"。** 否则下次同样错误再来一遍。
6. **完成即沉淀。** 有价值的信息不过夜，立马写进 CLAUDE.md。
7. **CLAUDE.md 写"为什么"不写"是什么"。** 代码能推导的不写，写代码推导不出来的。
8. **重复三次的协作模式写成 Skill。** 别每次都口头教 AI。
9. **知识资产分层管理。** raw/ 存源材料（不可变），wiki/ 存合成知识（Agent 维护），飞书作发布层（分享用）。
10. **朴素方案优先。** main-claude.md 比 MCP Server 有效一百倍，因为简单所以不出错。
