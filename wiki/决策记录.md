## LDAP 作为唯一身份源 (2026-05-15)

**背景**：三协议（HTTP/SMB/NFS）需要统一用户认证，避免各协议维护独立用户库。
**选项**：
| 方案 | 描述 | 优缺点 |
|------|------|--------|
| A：LDAP + posixAccount + sambaSamAccount | OpenLDAP 存储用户信息，Samba 直接查 ldapsam，NFS 用 UID 映射 | 优：一份数据三协议共用 / 缺：需要 Samba schema + NSS LDAP 配置 |
| B：tdbsam + authd 同步 | Samba 维护独立 tdbsam，authd 在注册时同步写入 | 优：Samba 配置简单 / 缺：两份数据不一致风险，无法支持 NFS UID 映射 |
**决策**：选 A
**理由**：拒绝 B 的原因是 NFS 必须依赖系统 UID 映射，tdbsam 无法提供。LDAP 是 NAS 多协议统一的唯一可行方案。Samba 的 ldapsam 后端成熟且文档完善。
**后果**：需要维护 Samba schema，注册用户时同时创建 LDAP 条目 + Linux useradd + 数据目录。事务回滚当前未实现（Demo 阶段手动清理即可）。

## POSIX ACL 作为唯一权限真相 (2026-05-15)

**背景**：三协议文件共享需要统一的权限控制。各协议各自维护 ACL 会导致权限不一致。
**选项**：
| 方案 | 描述 | 优缺点 |
|------|------|--------|
| A：POSIX ACL（setfacl/getfacl） | 所有权限存在文件系统的扩展属性中 | 优：三协议原生支持，零同步问题 / 缺：需要 LDAP UID 解析，Samba 有预检问题 |
| B：authd 维护独立权限数据库 | 在 SQLite 中维护文件和用户的权限映射表 | 优：API 友好 / 缺：三协议各自实现权限检查，SMB 和 NFS 无法读取 SQLite |
**决策**：选 A
**理由**：拒绝 B 的关键原因——SMB 和 NFS 是操作系统级别的文件服务，它们能读的唯一权限真相就是文件系统的 ACL。如果 authd 维护独立权限表，SMB/NFS 不会去查它。
**后果**：setfacl 不能直接传用户名（LDAP 用户不在 /etc/passwd），必须先查 UID 再用数字格式。Samba 在 POSIX ACL 前会先检查 group 权限，授权时需要同时 `chmod g+x`。

## 文件 API 独立于 WebDAV (2026-05-20)

**背景**：APP 需要文件管理能力，WebDAV 是现有协议之一，但 WebDAV 的 XML 响应不友好。
**选项**：
| 方案 | 描述 | 优缺点 |
|------|------|--------|
| A：authd 内实现 REST + JSON 文件 API | 自定义响应字段，不走 WebDAV | 优：灵活，客户端解析简单，可与 JWT 无缝集成 / 缺：多维护一套接口 |
| B：APP 直接用 WebDAV | 利用现有 Nginx WebDAV | 优：零开发 / 缺：XML 响应解析复杂，认证走 HTTP Basic 而非 JWT |
**决策**：选 A。WebDAV 作为第三方客户端兼容入口保留（端口 8081）。
**理由**：APP 需要自定义的响应结构（文件列表含权限字段）和 JWT 认证。WebDAV 的 auth_request 模式虽然也能验 JWT，但响应格式不可控。
**后果**：Maintain 两套文件接口：authd REST API（APP + Web 用）+ Nginx WebDAV（第三方客户端用）。API 前缀统一 `/api/`。

## mDNS 作为局域网发现协议 (2026-05-20)

**背景**：APP 需要在局域网内发现 NAS 设备，需要支持 P2P 直连场景。
**选项**：
| 方案 | 描述 | 优缺点 |
|------|------|--------|
| A：mDNS（zeroconf） | 通过 UDP 多播广播 _nas._tcp 服务 | 优：零配置，广泛支持 / 缺：需要 network_mode: host（bridge 隔离多播）|
| B：手动输入 IP | 用户手动输入 NAS 地址 | 优：不需要发现协议 / 缺：用户体验差 |
**决策**：选 A
**理由**：NAS 目标用户是家庭/个人，不能要求用户手动配 IP。mDNS 在 Linux 上通过 grandcat/zeroconf 实现，跨设备 1s 内完成发现。
**后果**：Docker 必须 `network_mode: host`。构造 PPP 网桥 IP。APP 端三层降级连接：mDNS → 缓存 IP → WiFi P2P。

## NFC phone_id 使用 ANDROID_ID (2026-05-28)

**背景**：NFC 碰一碰登录需要设备标识绑定，需要选择 phone_id 来源。
**选项**：
| 方案 | 描述 | 优缺点 |
|------|------|--------|
| A：Settings.Secure.ANDROID_ID | 64 位 hex，APP 重装不变 | 优：不需要权限，硬件绑定 / 缺：部分厂商实现有 bug（返回 64 位零）|
| B：随机 UUID + AsyncStorage | 首次启动生成，存本地 | 优：简单 / 缺：清缓存/重装后 UUID 变化，绑定失效 |
**决策**：选 A。NFC 模块不可用时回退方案 B。
**理由**：ANDROID_ID 是 Google 推荐的广告/设备标识方案，绑定到硬件签名，不需要运行时权限。UUID 方案在重装 APP 后 phone_id 变更，会导致用户需要重新绑定 NFC。
**后果**：需要处理少部分 ROM 返回 64 位零的兼容性问题（当前版本 code 中已处理）。

## PUF 存证：哈希链 + 签名分离 (2026-05-25)

**背景**：司法级存证需要保证文件操作的不可抵赖性，PUF 芯片提供设备唯一签名能力。
**选项**：
| 方案 | 描述 | 优缺点 |
|------|------|--------|
| A：同步写入 + 哈希链 | 文件操作时同步计算 SHA-256 哈希、追加到链、标记签名待补 | 优：操作即存证，不需要额外步骤 / 缺：PUF 签名延迟（puf-agent 未就绪时 signature 为空）|
| B：异步批量存证 | 定期扫描操作日志，批量生成存证包 | 优：PUF 签名可以批量 / 缺：操作和存证之间有时间窗口 |
**决策**：选 A
**理由**：存证必须在操作发生的同一时刻记录哈希和元数据，异步方案无法证明"操作发生时的状态"。PUF 签名可以延迟补充——signature 为 NULL 时验证方看到"PUF 签名待启用"。
**后果**：proof_records 表中有可能 signature 为 NULL。验证方需要处理这种情况。

## 用户注册不实现事务回滚（近期不修）(2026-05-15)

**背景**：用户注册涉及 LDAP AddUser → useradd → CreateDataDir 多步操作，任一步失败需要回滚前面的步骤。
**决策**：暂不实现事务回滚。Demo 阶段用户量极小，手动清理即可。
**理由**：完整的两阶段提交或补偿事务实现成本高，且 Demo 阶段几乎不会触发跨步骤失败。正式上线前需要实现。

## 时效管理简化：3 态 → 2 态 (2026-06-03)

**背景**：知识库文档时效从 fresh/stale/unknown 三态 + N 天阈值，简化为 fresh/unverified 两态，删除 N 天阈值。
**决策**：简化。高频开发节奏下 git diff 已覆盖全部 staleness 信号，N 天阈值是冗余复杂度。
**后果**：新创建的文章直接标 fresh 而非 unknown（短期内可接受）。

## 知识库 multi-match 检索 (2026-06-05)

**背景**：@kb 检索时单锚点模式只能返回一条结果，但用户问题往往涉及多个关联坑点（如 NFC + intent + 冷启动）。
**决策**：新增 multi-match 操作——提取 2+ 技术关键词 → 分别 grep → 合并同一文件邻近命中 → 跨文件排序 → 返回根因+关联+诊断（上限 800 tokens）。
**理由**：不需要改变已有 5 个单锚点操作，multi-match 是补充。复杂问题时自动触发，简单问题仍走单锚点。
**后果**：单锚点操作保持不变；multi-match 针对 2+ 关键词自动触发；检索结果上限 800 tokens 避免上下文膨胀；协议层和 kb-maintainer 同步更新。

## ADR 10: device_id 统一生成 (2026-06-08)

**背景**：NFC 碰一碰、mDNS 服务名、device-info 接口都需要一个唯一设备标识，各自生成或硬编码会导致不一致。
**选项**：
| 方案 | 描述 | 优缺点 |
|------|------|--------|
| A：读 `/host/etc/machine-id` → MD5 → 前12位 hex | 宿主机唯一标识，Docker 挂载只读 | 优：硬件绑定，跨容器重启不变，无需额外配置文件 / 缺：依赖正确挂载 |
| B：配置文件硬编码 DEVICE_ID | 手动设置环境变量或配置文件 | 优：简单 / 缺：每台机器需手动配置，无法自动化部署 |
| C：随机生成存入 SQLite | 首次启动生成 UUID 存入数据库 | 优：零配置 / 缺：数据库重建后 ID 变化，NFC 标签全部失效 |
**决策**：选 A。通过 `system.GetDeviceID()` 统一入口，mDNS 服务名（`NAS-{deviceID}-{IP}`）、`/api/device-info`、NFC 标签写入共用同一值。
**理由**：`/etc/machine-id` 是 systemd 生成的宿主机唯一标识，绑定硬件，除非重装系统否则不变。拒绝 B（手动配置不可靠）和 C（数据库重建后断裂）。
**后果**：Docker 必须挂载 `/etc/machine-id:/host/etc/machine-id:ro`。`GetDeviceID()` 是所有模块获取设备标识的唯一入口，禁止绕过。

## ADR 11: NFC 绑定存储在 LDAP (2026-06-08)

**背景**：NFC 碰一碰登录需要存储 phone_id ↔ username 映射关系。需要选择存储方案。
**选项**：
| 方案 | 描述 | 优缺点 |
|------|------|--------|
| A：LDAP `ou=nfc_bindings` + organizationalRole | phone_id 作为 cn，roleOccupant 指向用户 DN | 优：复用现有 LDAP 基础设施，不需要额外数据库 / 缺：organizationalRole 语义稍偏 |
| B：SQLite 新建 nfc_bindings 表 | 在 nas.db 中新增绑定表 | 优：SQL 查询灵活 / 缺：增加数据库 schema，LDAP 和 SQLite 两套存储 |
| C：直接存在用户 LDAP 条目的扩展属性 | 在用户条目上加自定义属性 | 优：数据集中 / 缺：OpenLDAP schema 扩展复杂，多设备绑定需要多值属性 |
**决策**：选 A。在 LDAP 中建 `ou=nfc_bindings,dc=nas,dc=local`，每条绑定用 `organizationalRole` 对象类（`cn={phone_id}`, `roleOccupant={user_dn}`）。
**理由**：LDAP 已是唯一身份源，NFC 绑定本质是身份关联，放在 LDAP 中一致性强。`organizationalRole` 是标准对象类，无需自定义 schema。一个 user 可以有多个 phone_id 绑定（多设备）。
**后果**：`POST /api/nfc-bind` 调 LDAP Add 写入绑定；`POST /api/nfc-login` 调 LDAP Search 查找 phone_id → 获得 username → 签发 JWT。不需要额外数据库迁移。

## ADR 12: container_name 规范 (2026-06-08)

**背景**：Docker Compose 自动生成容器名为 `<项目名>-<服务名>-<序号>`（如 `ldap-demo-openldap-1`），在不同环境下项目名变化会导致容器名不同，影响脚本和文档的一致性。
**选项**：
| 方案 | 描述 | 优缺点 |
|------|------|--------|
| A：compose 中显式指定 `container_name` | 每个服务用固定短名（openldap/ldap-init/nas-core/nas-web） | 优：跨环境一致，脚本可写死容器名 / 缺：同一主机不能运行多套实例 |
| B：保持 compose 自动命名 | 默认行为 | 优：灵活 / 缺：容器名不固定，文档和脚本需要动态查找 |
**决策**：选 A。所有 compose 服务用 `container_name` 固定容器名：`openldap`、`ldap-init`、`nas-core`、`nas-web`。
**理由**：开发/部署阶段单实例运行，不需要 compose scale。固定容器名后常用命令不再依赖 `docker compose exec` 的项目名上下文，可直接 `docker exec openldap ldapsearch ...`。
**后果**：同一 Docker daemon 下不能同时运行两套 nas-all-source 实例。部署脚本和 AGENTS.md 中的容器名全部使用短名。
