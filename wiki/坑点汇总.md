## 活跃坑点

### Docker 构建：golang 镜像拉取失败

**匹配关键词**：`golang:1.25`，`failed to fetch`，`not found`，`layer blob`
**版本**：Docker 任意版本
**现象**：`docker compose up --build` 时 `failed to fetch content descriptor ... from remote: not found`
**根因**：Docker Hub 部分 layer blob 在国内网络环境下偶发拉取失败
**修复**：
1. 先尝试 `docker pull golang:1.25` 单独拉取镜像（通常能解决瞬时网络问题）
2. 如持续失败，才考虑降级镜像版本
**预防**：注意 `golang.org/x/sync@v0.20.0` 等间接依赖需要 `go >= 1.25.0`，golang:1.24 无法编译

### WiFi P2P：桌面版 Ubuntu 不可用

**匹配关键词**：`P2P`，`FAIL`，`p2p_group_add`，`NetworkManager`，`D-Bus`
**版本**：桌面版 Ubuntu（有 NetworkManager）
**现象**：桌面版 Ubuntu 上，容器内 `wpa_cli p2p_group_add` 命令执行无效果，APP 端 P2P 发现不到设备。宿主机直接执行 `sudo wpa_cli p2p_group_add` 也返回 `FAIL`
**根因**：WiFi 芯片同一时间只能被一个 wpa_supplicant 实例控制。桌面版 Ubuntu 的 NetworkManager 通过 `wpa_supplicant -u`（D-Bus 模式）接管 WiFi 硬件，容器内独立 wpa_supplicant 无法绑定已被占用的 WiFi 接口
**修复**：`start.sh` 已内置环境检测——发现 D-Bus 模式时自动跳过 P2P 初始化，APP 端走 mDNS 局域网发现
**预防**：NAS 硬件（Ubuntu Server，无 NetworkManager）上 P2P 自动可用，无需代码修改

### POSIX ACL 授权静默失败

**匹配关键词**：`setfacl`，`Invalid argument`，`ACL`，`Option -m`
**版本**：所有容器环境
**现象**：`POST /api/share/permission` 返回 200 OK，但 `getfacl` 查不到新设的 ACL 条目，用户权限未实际变更
**根因**：`setfacl -m user:bob:rwx` 在容器内执行时，`setfacl` 需要将用户名解析为 UID。LDAP 用户不在 `/etc/passwd` 中，NSS 对其不可见，`setfacl` 返回 `Option -m: Invalid argument near character 6`。`.Run()` 静默丢弃错误输出
**修复**：`system/os.go` 中 `SetACL` 和 `RemoveACL` 改用数字 UID 格式（`user:1002:rwx`），先通过 LDAP 查 UID 再传给 setfacl。`hasACLWrite` 同理。所有 `exec.Command().Run()` 改为 `CombinedOutput()`，失败时记录日志

### NEARBY_WIFI_DEVICES 未授权导致 discoverPeers 持续 BUSY

**匹配关键词**：`BUSY`，`reason=0`，`discoverPeers`，`NEARBY_WIFI_DEVICES`
**版本**：Android API 33+
**现象**：调用 `discoverPeers` 始终返回 `onFailure(reason=0)`，日志显示 "发起 P2P 发现失败 (code=0)"，没有任何 SecurityException
**根因**：Android 13+ 上 `NEARBY_WIFI_DEVICES` 是运行时危险权限。未授权时不抛 SecurityException，而是返回 `reason=0`（BUSY），无法从 API 层面区分"没权限"和"框架忙"。`hasLocationPermission()` 在 API 33+ 直接 `return true`，完全没检查此权限
**修复**：`hasLocationPermission()` 中对 API 33+ 显式检查 `checkSelfPermission(NEARBY_WIFI_DEVICES)`
**预防**：在 AGENTS.md 致命约束中声明此权限是运行时危险权限

### P2P DISCOVERY_STOPPED 误判为超时

**匹配关键词**：`stopPeerDiscovery`，`DISCOVERY_STOPPED`，`resolveError`，`cleanup`
**版本**：全部
**现象**：`discoverPeers` 成功返回，但 APP 立即显示"发现超时，未找到 NAS 设备"。日志显示 `stopPeerDiscovery 完成` → `DISCOVERY_STOPPED` 广播 → `resolveError` 调用
**根因**：`startDiscovery()` 前调用 `stopPeerDiscovery()` 清理 BUSY 状态，但它产生的 `DISCOVERY_STOPPED` 广播被自己的 Receiver 收到，误判为 discoverPeers 超时。`resolveError` 调用后 `cleanup()` 注销了所有 Receiver，真正的 discoverPeers 成功时接收器已不存在
**修复**：增加 `ourDiscoveryStarted` 标志位，区分"主动停止"和"被动超时"
**预防**：P2P 状态机中所有广播事件都需要加来源区分

### P2P PEERS_CHANGED 重复触发

**匹配关键词**：`PEERS_CHANGED`，`requestPeers`，重复连接，`connectionAttempted`
**版本**：全部
**现象**：`requestPeers` 回调被触发 3 次，每次都遍历设备列表并调用 `connectToDevice`，日志中出现 3 条 "发起连接请求 → DIRECT-xx"
**根因**：Android 一次设备列表变化可能触发多次 `PEERS_CHANGED` 广播，导致 `requestPeers` 回调重复执行
**修复**：增加 `connectionAttempted` 标志位，连接操作只执行一次

### USB 网络共享 mDNS 可达但 TCP 不通

**匹配关键词**：`USB`，`mDNS`，`ping`，`timeout`，`USB 共享`
**版本**：全部
**现象**：手机通过 USB 共享电脑网络时，mDNS 能发现 NAS（UDP 多播可达），APP 显示"已连接"，但 `/api/ping` 超时、登录失败
**根因**：UDP 多播可跨越 USB 线缆（电脑 WiFi 网卡发出多播 → USB → 手机），但 TCP 需要双向路由——手机路由表中没有 NAS 所属网段的出口，HTTP 请求发出即丢弃
**修复**：mDNS 发现后延长 ping 超时（6s + 重试），ping 失败仍保留 mDNS 发现的 URL（不跌到缓存层）
**预防**：开发测试时手机直连同一 WiFi，不走 USB 共享

### 文件 API path=/ 返回 403

**匹配关键词**：`path=%2F`，`403`，`validatePath`，`/data/`
**版本**：全部
**现象**：登录成功后 HomeScreen 数据加载失败，后端日志 `GET /api/files?path=%2F → 403`
**根因**：后端 user 角色的 `ValidatePath` 要求请求路径以 `/data/{username}/` 为前缀。`path=/` 不满足。后端只在 path 参数完全为空时走默认路径映射
**修复**：APP 端发送 path 参数时传空字符串而非 `/`

### NFC 冷启动 intent 数据丢失

**匹配关键词**：`NFC`，`冷启动`，`AAR`，`NDEF_DISCOVERED`，`MAIN`，`intent`
**版本**：国产 ROM（已确认小米、OPPO）
**现象**：触碰 NFC 标签后 AAR 成功冷启动 APP，但 NfcModule 拿不到 NFC intent（空的 action 和 extras），NfcScanScreen 不会自动跳转
**根因**：部分国产 ROM 将 AAR 唤起的 `NDEF_DISCOVERED` intent 降级为 `MAIN` action，并丢弃 extras（无 Tag 对象）。NfcModule 在 `onNewIntent` 中拿到的就是普通的启动 intent
**修复**：当前方案——AAR 只负责打开 APP，用户进入 NfcScanScreen 后通过前景调度读标签。后续通过 `enableReaderMode` 绕过 intent 分发解决
**预防**：`MainActivity` 中用 `companion object` 静态变量缓存冷启动 intent，配合 `try-catch` 兜底 RN 0.85 New Architecture 限制

### RN 0.85 New Architecture 禁止 reactNativeHost

**匹配关键词**：`RuntimeException`，`reactNativeHost`，`New Architecture`，`FabricUIManager`
**版本**：React Native >= 0.85
**现象**：`onCreate` 中访问 `reactNativeHost.reactInstanceManager` 直接抛 `RuntimeException: You should not use ReactNativeHost directly in the New Architecture`
**根因**：RN 0.85 默认启用 New Architecture（Fabric），`FabricUIManager` 模式下禁止直接访问 `ReactNativeHost`
**修复**：NFC 冷启动缓存用 `companion object` 静态变量存储，不经过 RN bridge。`onNewIntent` 中加 `try-catch` 兜底
**预防**：在 AGENTS.md 致命约束中声明此限制

### document-picker 9.x 不兼容 RN 0.74+

**匹配关键词**：`GuardedResultAsyncTask`，`document-picker`，`编译错误`
**版本**：`react-native-document-picker` 9.x + React Native >= 0.74
**现象**：`pnpm android` 报 Java 编译错误，全部指向 `GuardedResultAsyncTask` 符号不存在
**根因**：`react-native-document-picker` 9.x 全系列依赖 RN bridge 的 `GuardedResultAsyncTask` 类，此类在 React Native 0.74+ 已移除
**修复**：替换为 `@react-native-documents/picker` 12.0.1
**预防**：升级 RN 大版本时同步检查所有原生依赖的兼容性

### mDNS wlx 接口名未被白名单识别

**匹配关键词**：`wlx`，`mDNS`，`isPhysicalOrP2P`，`0 设备`，`接口过滤`
**版本**：USB WiFi 网卡（MAC 命名接口）
**现象**：mDNS 服务启动正常，但 APP 端发现不到 NAS 设备（返回 0 设备），`pickIPs()` 没有在任何接口上注册服务
**根因**：`isPhysicalOrP2P()` 函数白名单只允许 `wlp`/`wlan`/`eth`/`enp`/`p2p-` 前缀的接口名。USB WiFi 网卡按 MAC 地址命名的 `wlx` 开头的接口被过滤掉，导致该接口上的 IP 不被注册
**修复**：在 `isPhysicalOrP2P()` 白名单中增加 `wlx` 前缀
**预防**：新增网卡类型时检查接口命名前缀是否在白名单中

### exFAT 文件名不能含冒号

**匹配关键词**：`exFAT`，`冒号`，`:`，`无效的参数`，`tar`，`镜像`
**版本**：exFAT 文件系统（U 盘常用格式）
**现象**：将 Docker 镜像 tar 文件（如 `nas-images:1.1.0.tar`）拷贝到 exFAT 格式 U 盘时，报错"无效的参数"，拷贝失败
**根因**：exFAT 文件系统禁止文件名中出现冒号 `:` 字符（与 NTFS/ext4 不同），而镜像 tar 文件常用 `镜像名:标签.tar` 格式命名
**修复**：镜像文件命名改用 `-` 替代 `:`，如 `nas-images-1.1.0.tar`
**预防**：导出文件到可移动介质前确认目标文件系统限制（FAT32/exFAT 均不支持 `:`）

### 移动硬盘写缓存丢数据

**匹配关键词**：`移动硬盘`，`T7`，`sync`，`拔线`，`文件丢失`，`写缓存`
**版本**：所有 USB 移动硬盘（特别是 SSD）
**现象**：`cp` 大文件到 Samsung T7 移动硬盘后，立即拔掉 USB 线，重新插入后发现文件内容为空或不存在
**根因**：Linux 内核的写缓存机制——`cp` 返回成功时数据仍在内存缓存中，尚未真正写入磁盘。USB 拔线时缓存中的数据丢失
**修复**：`cp` 完成后立即执行 `sync` 命令强制刷盘，或使用 `cp --preserve=all && sync` 组合。卸载前也必须 `umount` 而非直接拔线
**预防**：所有对外部存储的写操作后执行 `sync`；部署脚本中关键文件拷贝后加 `sync`

### docker compose up 复用旧容器

**匹配关键词**：`docker compose up`，`复用`，`image:`，`不重建`，`旧容器`
**版本**：Docker Compose v2
**现象**：修改 `docker-compose.yml` 中服务的 `image:` 字段后，执行 `docker compose up -d`，容器没有使用新镜像，仍运行旧容器
**根因**：`docker compose up` 检测到同名容器已存在且配置未变时，直接复用旧容器而不重建。仅改 `image:` 标签不被视为"配置变更"
**修复**：先执行 `docker compose down` 停止并删除容器，再 `docker compose up -d`。或使用 `docker compose up --force-recreate -d`
**预防**：部署流程中固定使用 `docker compose down && docker compose up -d` 模式；开发中使用 `--build` 确保镜像也重建

### compose build 自动生成的镜像名

**匹配关键词**：`compose build`，`镜像名`，`目录名-服务名`，`image:`
**版本**：Docker Compose v2
**现象**：`docker compose build` 后生成的镜像名为 `目录名-服务名`（如 `nas-core-nas`），而非预期的标准化名称
**根因**：Docker Compose 默认用 `<项目目录>_<服务名>` 或 `<目录名>-<服务名>` 格式命名构建产物。如果 compose 文件中没有显式 `image:` 字段，镜像名不可控
**修复**：在 compose 文件的 build 服务中同时添加 `image:` 字段指定标准名（如 `image: nas-core:latest`），这样 build 后镜像同时拥有标准 tag
**预防**：所有 compose 服务的 build 块都应包含 `image:` 字段

### NFC 碰一碰 device_id 校验 403

**匹配关键词**：`machine-id`，`device_id`，`403`，`NFC`，`nfc-login`，`校验失败`
**版本**：所有部署环境
**现象**：APP 触碰 NFC 标签后调用 `POST /api/nfc-login`，后端返回 403 "device_id 校验失败"。开发机和目标 NAS 机返回的 device-id 不同
**根因**：NFC 标签中写入的 `device_id` 来自开发机 `/etc/machine-id` 的 MD5 值，部署到目标机后容器内 `/etc/machine-id` 是目标机的值，两者不匹配。Docker 未挂载宿主机的 machine-id
**修复**：确认 `docker-compose.yml` 中挂载了 `/etc/machine-id:/host/etc/machine-id:ro`，并确认 `GetDeviceID()` 正确读取 `/host/etc/machine-id`。NFC 标签写入前确认目标机的 device-id
**预防**：部署 checklist 中增加"确认 machine-id 挂载"项；NFC 标签烧录脚本从目标机实时获取 device-id
